# DangCharge Convention

출처: 팀 Notion `Convention` 페이지. 내용이 바뀌면 이 파일도 같이 갱신한다.

## 브랜치

| 브랜치 | 역할 |
| --- | --- |
| `main` | 최종 Merge 브랜치. 항상 배포 가능한 상태 |
| `develop` | 개발 통합 브랜치. 모든 기능이 정상 동작하는 상태로 유지 |
| `구현기능타입/기능명` | 작업 브랜치. 예: `feat/header-component` |

- 작업 브랜치는 `develop`에서 분기하고 `develop`로 병합한다. `main`에서 직접 분기하거나 `main`으로 직접 PR을 올리지 않는다.
- 브랜치 이름의 타입은 아래 커밋 키워드를 쓰고, 기능명은 영어 kebab-case로 쓴다.
- 브랜치를 임의로 만들거나 옮기지 않는다. 지금 체크아웃된 브랜치에서 작업하고 커밋하며, 푸시도 같은 이름의 원격 브랜치로 한다. `main`에서 작업했으면 `main`으로 푸시한다.
- 새 브랜치는 사용자가 요청했을 때만 만든다. 그때 위 분기 규칙과 이름 규칙을 따른다.

## 커밋 메시지

형식은 `키워드: 내용`이고, 내용은 영어로 쓴다.

| 키워드 | 설명 |
| --- | --- |
| `init` | 초기 세팅 |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그/에러 resolve |
| `docs` | 문서 수정, 파일 삭제, 파일명 수정 등 |
| `chore` | 빌드 테스트 업데이트, 패키지 매니저 설정, 주석 추가 등 |
| `code review` | 코드리뷰 반영 |
| `refactor` | 프로덕션 코드 리팩토링 |

예시:

```
feat: add charging station producer
fix: resolve kafka serializer null pointer
code review: rename topic constants
```

- 표에 없는 키워드(`style`, `test`, `perf` 등)는 쓰지 않는다. 가장 가까운 키워드를 고른다.
- 한 커밋에는 한 키워드에 해당하는 변경만 담는다.

## PR

- 작업 브랜치를 원격으로 푸시하면 묻지 않고 PR까지 바로 만든다. 그 브랜치의 PR이 이미 열려 있으면 새로 만들지 않는다.
- `main`이나 `develop`에서 직접 푸시한 경우에는 PR을 만들지 않는다.
- base는 `develop`, head는 작업 브랜치. `develop`가 원격에 없으면 임의로 `main`을 base로 쓰지 말고 사용자에게 먼저 알린다.
- 제목도 커밋과 같은 `키워드: 내용` 형식으로 쓴다.
- 본문은 [pr-template.md](pr-template.md)의 구조를 그대로 쓴다. 섹션을 지우지 말고, 해당 없는 섹션은 `없음`으로 채운다. 체크박스는 실제로 수행한 항목만 체크한다.
- 팀 규칙상 이 템플릿은 각 레포지토리의 `.github` 폴더에도 둔다. 레포에 `.github/pull_request_template.md`가 있으면 그 파일을 우선한다.

## 코딩 컨벤션

- 단위 개발이 끝날 때마다 사용자에게 묻지 않고 바로 커밋한다. 하나의 기능·수정·리팩토링처럼 독립적으로 설명할 수 있는 변경이 한 단위이고, 빌드가 깨지지 않는 상태에서 커밋한다.
- 커밋 메시지는 위 커밋 규칙을 따르고, 여러 단위를 한 커밋에 몰아넣지 않는다.
- 자동으로 하는 것은 커밋까지다. 푸시는 사용자가 요청했을 때만 하고, PR은 위 PR 규칙대로 푸시에 이어서 만든다.
- 코드 스타일은 Notion 페이지에 아직 정해진 내용이 없다. 정해지기 전까지는 주변 코드의 스타일을 따른다.
